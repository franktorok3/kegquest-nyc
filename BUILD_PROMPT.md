# Reusable Codex build instructions

Build and deliver KegQuest NYC: an excellent mobile-first New York brewery discovery app using Next.js App Router, TypeScript and Tailwind. Work through implementation, tests, GitHub and authorized Vercel production deployment; do not end with a plan or unverified URL.

1. Inspect the working directory and relevant instructions. Confirm the authorized GitHub identity, Vercel team/project and production branch. Reuse this repository where available; do not alter unrelated projects. The user authorizes creation of this app's repository/project and public deployment, not spending, unrelated migrations, or sending messages.
2. Preserve the editorial cream, forest-green and orange field-guide design. Provide strong mobile typography, original illustrated hero art, responsive cards, keyboard navigation, reduced motion, useful empty states, and a clear source methodology page.
3. Implement searchable brewery directory, all five borough filters, style discovery, browser-local saved places, detail pages, official website links and verified-address map links. Make missing information explicit. Never treat a producer without a verified taproom as a guaranteed walk-in destination.
4. Discover real entries from the NYC Brewers Guild and primary brewery websites. Use a reviewed URL registry. Respect robots.txt, explicit user-agent rules, crawl delays, timeout/size limits, access restrictions, and low request rates. Fail closed when robots cannot be retrieved except a genuine 404. Review redirects and never bypass access controls.
5. Persist source URL, attempted timestamp, success timestamp and evidence for every observed field. Separate draft menus from packaged beer and general catalogues. Only publish beer name/style/ABV from deterministic tested adapters targeting the correct location's explicitly labeled draft list. Do not use AI guesses. Unsupported/blocked menus are unavailable.
6. Keep missing details null; publish addresses/hours only against reviewed evidence. Include source-provided image previews with provenance and a clear fallback. Prominently preserve event-only or closure notices.
7. Use recently checked (<=36h), aging (<=7d), stale (>7d), and unavailable states. Exclude stale/unavailable draft menus from style recommendations. Compute freshness at request time. Make source links and timestamps visible.
8. Implement a persistent daily ingestion path. This repository uses GitHub Actions to crawl, test, build and commit snapshots; the Vercel Git integration publishes main. Verify an actual scheduled/manual run and the resulting production update. Do not claim scheduling works from a YAML file alone.
9. Test data lineage, draft/can isolation, parser missing-field failure, robots denial/failure, freshness boundaries, filter combinations, empty states, saved-place persistence, detail navigation and narrow-screen overflow. Run a production build and dependency audit. Fix errors before release.
10. Maintain comprehensive README documentation covering setup, sources, limitations, scheduling, adapters, tests and deployment. Commit and push source without secrets or raw copyrighted page archives. Deploy to the confirmed Vercel project and check the anonymous production vercel.app URL in a real browser. Deliver the live URL and repository URL, describe verified coverage accurately and disclose remaining blockers. Never substitute Ready/preview for anonymous live verification.
